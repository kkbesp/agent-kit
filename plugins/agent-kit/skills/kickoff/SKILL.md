# Kickoff: проект, который агент берёт с холодного старта

Результат — документы и навигатор, **не код**. Пакеты не ставятся, приложения не создаются: это делает первая карточка. Каждая фаза заканчивается файлом и коротким подтверждением владельца; молча не переходить к следующей, если в ней был существенный выбор.

Шаблоны лежат рядом: `templates/project/`. Копируй их в проект и заполняй, `{{…}}` не оставляй.

## 0. Режим и исходная точка

Проверь `git status`, корень, существующие `README`, `AGENTS.md`, `CLAUDE.md`, `docs/`, план. Определи режим:

- **Новый** — пустой или почти пустой репозиторий.
- **Существующий** — есть код: сначала прочитай структуру, манифесты, запуск; решения выводи из кода и подтверждай у владельца, не придумывай заново.
- **Переписывание** — есть прежние версии/архив: это источник подтверждённых ошибок и удачных решений, не архитектуры. Новая версия от архива не зависит (никаких импортов, symlink, общих конфигов).

Ничего не перезаписывай: существующий документ дополняй, конфликт показывай владельцу.

## 1. Интервью → решения и уроки

Спрашивай пачками до 4 вопросов (инструмент вопросов, если есть), с рекомендуемым вариантом первым. Минимум:

1. Кто пользователи и какой **один главный путь** они проходят (действие → сохранённый итог).
2. Что такое **первый видимый результат** — что владелец откроет и увидит в конце первой карточки.
3. Границы **v1** и что **явно не входит** (отложенное в v2 тоже записать).
4. Ограничения: сроки, серверы и окружения, бюджет и платные сервисы, данные и приватность, обязательные интеграции.
5. Прежний опыт: старые версии, конкуренты, журналы, жалобы пользователей — что сохранить, что исправить.

Запиши в `docs/product/decisions.md` пронумерованными решениями (решение → причина → дата → что исключает) и в `docs/product/lessons.md` уроки в форме «наблюдение → вывод → решение → чем проверить». Наблюдение отличай от гипотезы. Личные данные и приватные логи не копируй — только обезличенный вывод.

## 2. Стек → готовые решения и архитектура

Составь список потребностей (UI, сборка, API, БД, auth, фон/очереди, файлы, уведомления, деплой, наблюдаемость — только нужные). Для каждой:

- Сначала **готовое средство**: штатная возможность платформы, зрелая библиотека, готовый компонент. Самописное — только с причиной.
- Версия — из registry **сейчас** (`npm view <pkg> version peerDependencies`, `pip index versions`, релизы GitHub), документация — этой версии, лицензия, активность сопровождения. Последняя версия ≠ совместимая: проверь peer dependencies связки целиком.
- Реальный выбор (2–3 варианта) показывай владельцу с рекомендацией; очевидное не выноси на голосование.

Используй skill `source-driven-development`. Запиши:

- `docs/engineering/solutions.md` — таблица «задача → средство@версия → почему → границы/риски → первый потребитель (карточка)». Зависимость появляется в проекте вместе с первым потребителем.
- `docs/engineering/architecture.md` — модули и клиенты, **один владелец каждого изменения данных**, границы доверия, где хранится что, как запускается локально.

## 3. Roadmap → карточки пользовательских результатов

`ROADMAP.md` по шаблону — единственный реестр задач. Правила нарезки:

- Карточка = **пользовательский результат** («кто → действие → сохранённый итог»), а не слой («сделать backend», «настроить БД»). Общие механизмы (ошибки, права, логи, уведомления) входят в первую карточку, которой они нужны.
- **Первая карточка** — одна команда поднимает систему, и пользователь проходит минимальный путь до видимого результата.
- Порядок в файле = приоритет; группируй по рубежам «ближайший проверяемый результат».
- **DEPS — только обязательные готовые входы**: если приёмке нужен результат другой карточки, он в DEPS; общая область — не зависимость. Не добавляй всё предыдущее «для порядка».
- Поля: `STATUS · OWNER · DEPS · CLAIM` первой строкой; затем «Результат / scope», «Ownership / вход» (номера решений и уроков), «Приёмка / проверка» (где, чем, что видно), «Порядок внутри карточки» (проходы, первый показывается сразу), «STOP». Размер — 1–3 прохода, каждый проверяем отдельно.
- Приёмка реалистична: локальная среда, тестовые данные, браузер. Отсутствие production-доступа или бюджета — внешний остаток в EVIDENCE, не блокер. Нельзя требовать несуществующий стенд или аварию в production.
- ID с префиксом проекта (`ABC-001`), постоянные: не перенумеровывать.

## 4. Каркас для агентов

Скопируй и заполни:

- `AGENTS.md` — правила проекта, архитектурные границы, команды, раздел «Частые ошибки» (начальные строки — из уроков интервью).
- `CLAUDE.md` — одна строка `@AGENTS.md` (одна копия правил на всех агентов).
- `docs/engineering/delivery.md` — порядок работы: как взять задачу, защита темпа, делегирование, продолжение.
- `scripts/roadmap.mjs` — навигатор; если есть `package.json`, добавь скрипт `"roadmap": "node scripts/roadmap.mjs"`.
- `.gitignore` — каталог временных артефактов `.artifacts/`.

## 5. Приёмка kickoff

- `node scripts/roadmap.mjs check` — exit 0; `node scripts/roadmap.mjs` показывает первую карточку свободной.
- `rg -n '\{\{' AGENTS.md ROADMAP.md docs/` — пусто: незаполненных плейсхолдеров не осталось.
- Каждое обещание v1 из решений покрыто карточкой; у каждой карточки есть проверяемая приёмка; DEPS не образуют лишних цепочек (проверь промежуточное состояние: что станет доступно после DONE первой карточки).
- Независимая проверка свежим агентом (`verifier` или новый контекст) с вопросом: «Можешь ли ты взять {{PREFIX}}-001 с холодного старта, прочитав только AGENTS.md и вывод навигатора? Что неясно или противоречит?» Исправь найденное в исходном документе.
- Покажи владельцу итог: путь пользователя, первые 3 карточки, принятые решения стека. Коммит — после его согласия.

## Анти-паттерны

- Писать код, ставить пакеты или создавать пустые каталоги приложений на этапе kickoff.
- Выбирать стек по памяти, без registry и документации версии.
- Отдельные файлы планов, TODO-списков, отчётов рядом с ROADMAP.
- Эпики-исследования вместо пользовательских результатов; карточка «написать тесты».
- Сотни карточек сразу: детализируй ближайший рубеж, дальние — крупно, уточняются при подходе.
