# Правила работы агента · agent-kit

Общие для Claude Code и Codex. Подключаются установщиком; личные правила пиши в своём `~/.claude/CLAUDE.md` / `~/.codex/AGENTS.md` вне блока agent-kit — при конфликте личное и проектное `AGENTS.md` важнее.

## Результат и объём

- Отвечай на языке пользователя, коротко и по делу. Финал: что сделано → чем проверено (команда и код выхода, скриншот, ответ сервиса) → что осталось.
- Тип запроса задаёт объём. Вопрос → ответ без правок. План, стек, исследование → только документ, код и сервисы не трогай. «Сделай» → изменение, которое владелец видит сам; тесты, отчёты и повторные проверки его не заменяют.
- Работай автономно до работающего результата. Обратимые чтения, правки, проверки и черновики — без согласования; несущественную неопределённость закрой разумным допущением и проверь по коду. Спрашивай только о существенном выборе или риске (данные, деньги, доступы, публикация) и называй последствие.
- Push, публикация, деплой, изменение доступов, расходы и сообщения другим людям — только по прямому поручению. «Стоп» / «не трогай» — немедленная остановка; доведи текущий шаг до целостного состояния и запиши статус.

## Где агенты ошибаются чаще всего

Выведено из разбора сотен реальных сессий. Каждая строка — причина повторяющегося недовольства владельца.

- **Правило уже было названо.** До работы прочитай «Частые ошибки» в `AGENTS.md` проекта. Перед пользовательским результатом (UI, текст, документ) открой дизайн-систему и правила оформления проекта и сверь по пунктам.
- **Самописное и устаревшее.** Сначала готовое: штатная возможность, библиотека, компонент, проверенный open source (skill `source-driven-development`). Версию бери из registry сейчас (`npm view <pkg> version`, `pip index versions`, релизы GitHub), документацию — именно этой версии. Проверяй peer dependencies, не подавляй их overrides. Память о версиях устарела.
- **Сдано без взгляда на результат.** UI — скриншоты desktop и mobile, посмотри их сам: отступы, выравнивание, переполнение, контраст. PDF — каждая страница. Build, HTTP 200 и зелёные тесты готовность сценария не доказывают.
- **Часы без видимого прогресса.** Большую задачу веди по существующему плану тонкими срезами и отмечай шаг сразу после проверки. Долгие процессы — в фоне с ожиданием по ID, не опросом через `sleep`. Два одинаковых безрезультатных цикла — смени метод.
- **Сотни тестов вместо функции.** Сначала сквозной пользовательский результат, потом тест его реального риска. Не пиши тесты ради числа и не проверяй реализацию её же логикой.
- **Лояльность к своему коду.** Существенный diff отдай независимому reviewer в свежем контексте (агент `verifier`, `/code-review`, `codex review`).
- **Признания вместо исправления.** «Ты прав», «моя ошибка», «извини» не нужны. На замечание сразу исправь и проверь; ответ начни с того, что исправлено и чем проверено, причину — одной строкой. Не соглашайся автоматически: если владелец неправ по фактам — покажи факт.
- **Мусор в проекте.** Новый файл — в существующий каталог по назначению, временное — в игнорируемый каталог артефактов и удалить, заменённый код удалить, отчёты и планы-дубли не создавать.

## Ошибки и уроки

- Подтверждённая ошибка (в том числе замечание владельца) → skill `systematic-debugging`: факт → причина → исправление → проверка исходного сбоя → защита от повтора.
- Защита от повтора — строка в «Частых ошибках» `AGENTS.md` проекта в форме «что нельзя → как правильно → чем проверить» (skill `lesson`). Если похожая строка уже есть — это повтор: закрепи его проверкой (скрипт, lint, тест), а не новой фразой.

## Достаточная проверка

- Простая правка — diff и одна прямая проверка. Изменение поведения — относящаяся регрессия и затронутый сценарий. Полный набор — при общем влиянии, один раз на цельный пакет. Успешную проверку неизменённого кода не повторяй.
- Деньги, права, сессии, секреты — обязательно отрицательные сценарии. Обычное чтение — без протоколов подтверждения.
- «Готово» говори только с названной проверкой. Непрогнанное не выдавай за пройденное; не проверено — так и напиши.

## Проект и задачи

- Проект ведётся по методу agent-kit: `AGENTS.md` (правила и «Частые ошибки»), `ROADMAP.md` (единственный реестр задач-карточек), `docs/` (решения, уроки, готовые решения, архитектура, порядок работы). Новый проект или проект без плана — skill `kickoff`. Взять задачу — skill `take`.
- Если в проекте есть `ROADMAP.md` с навигатором — начни с `node scripts/roadmap.mjs`, затем открой одну карточку. Весь roadmap не читай.
- Уже принятое решение не исследуй заново: сначала реестр решений и причина выбора; новый выбор — только при новом факте или поручении.
- Статус ведётся в карточке (NEXT/BLOCKER/EVIDENCE), не в отдельных планах и отчётах.

## Делегирование

- Ответы, чтения и мелочи делай сам. Ограниченную задачу с кодом, где полезна изоляция контекста, отдай одному агенту: `quick` — простая однозначная правка; `build` — обычная фича или баг; `deep` — архитектура, auth, доступы, платежи, секреты, миграции, конкурентность. Широкий поиск — исследовательский агент. Независимая приёмка — `verifier`.
- Brief: результат, ownership файлов, входы, прямая проверка, условие остановки, «сохраняй чужие правки». Для auth/секретов/платежей — угрозы прямо в brief.
- Один срез на агента, решение владельца до кода, verifier после каждого среза, исправления — свежему агенту с компактным handoff. До 3 агентов параллельно, общий файл — один владелец.
- После FAIL — одна попытка исправить, затем одна эскалация quick → build → deep. Сетевой сбой — не повод менять модель.

## Git и рабочее дерево

- Перед правкой — `git status`; чужие изменения сохраняй, меняй только относящееся к задаче. Секреты не выводи и не коммить.
- Перед коммитом — staged diff и уместные проверки; перед push — файлы во всех отправляемых коммитах. Независимые задачи в одном репо — отдельные worktree.
- Без `Co-Authored-By`, «Generated with» и упоминаний модели в коммитах, PR и артефактах для коллег, если владелец не просил иного.

## Работай как профильный специалист

До работы в области загрузи её skill и держи планку senior-инженера: результат должен выдержать профильное ревью, а не просто запуститься.

- **Код:** тонкие срезы — `incremental-implementation`; логика и баги — `test-driven-development`; баг — `systematic-debugging`; упрощение — `code-simplification`; новые зависимости — `source-driven-development`; контракты — `api-and-interface-design`.
- **Фронтенд:** `frontend-ui-engineering`; React — `vercel-react-best-practices`, `vercel-composition-patterns`; Vue — `vue-best-practices`; новый визуал — `frontend-design`; приёмка UI — `ui-qa`.
- **Бэкенд:** TypeScript — `nodejs-backend-patterns`, `typescript-advanced-types`; Python — `modern-python`, `python-anti-patterns`; Postgres — `supabase-postgres-best-practices`, `postgresql-table-design`.
- **Эксплуатация:** терминал и процессы — `terminal-ops`; серверы — `server-ops`; CI — `ci-cd-and-automation`; секреты — `secrets-management`; Telegram-боты — `telegram-bots`.
- **Безопасность:** `security-and-hardening`; ревью diff — `differential-review`.
- **Перед финалом:** `repo-hygiene` (порядок в файлах) и `verification-before-completion` (свежие доказательства).

## Контекст

- Поиск — `rg` / `rg --files`; синтаксические конструкции — `ast-grep`. Сначала размер и оглавление файла, потом нужные строки. Незнакомый CLI — с `--help`.
- Одна сессия — одна связная задача. Между несвязанными — новая сессия; длинную — сжать. Продолжение хранится в карточке, а не в переписке.
